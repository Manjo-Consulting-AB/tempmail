## What this is

**Mail Shield** is a *secondary email environment* — permanent personal addresses, temporary addresses, and automation — operated by Manjo Consulting AB on the domain `manjo.me`. It is written in plain PHP (no framework, no build step). A visitor can:

- create a **Timed address** that receives mail for 24 hours (Pro: 1–7 days) and then deletes itself;
- keep up to **10 Sticky addresses** — long-lived, no expiry (Pro only);
- wire the inbox into other systems — RSS, webhooks, Pushover, digests — or run the **Client Agent** on their own mail server to filter mail locally.

Temporary email is therefore **one feature, not the identity**. The paid "Pro" tier covers magic-link login, a saved profile, the RSS feed of messages and Paddle billing; the "Client Agent" subsystem is mostly separate and end users install it on their own mail server, driven by RSA-signed webhooks from this backend. Positioning and the approved copy are in brief §2 and §8 — read the brief before writing any user-facing text.

**Naming rule:** the product is called **Mail Shield** in all user-facing copy. The two kinds of address are **Sticky addresses** (code: `is_personal = 1`, "personal") and **Timed addresses** (code: temp addresses, `include_temporary`) — never "personal" or "temporary addresses" in copy; "temporary email" survives only as an SEO keyword for the category (brief §2, §14). The internal identifiers `TEMPMAIL_APP`, `window.tempMailConfig`, `class TempMailApp`, the `TEMPMAIL_*` env vars, database names and file names deliberately keep the old name — do not "finish" the rename in code.

There is no `README.md` at the repo root — this file and `documentaion/` are the closest thing to onboarding docs. Several docs under `documentaion/` and `client/` are written in Swedish, as are many code comments; expect to read/write Swedish comments when touching existing code, but prefer English for new comments unless matching surrounding style. (`documentaion/` is a real, intentional typo in the directory name — don't "fix" it, it is used as a path elsewhere.)

## Tech stack

- **Language**: PHP, procedural with some classes. No framework (no Laravel/Symfony).
- **Database**: MySQL/MariaDB via PDO (`$pdo` global set up in `config.php`).
- **Mail parsing**: `php-mime-mail-parser/php-mime-mail-parser` and `zbateson/mail-mime-parser` (see `composer.json`), used by `MailParser` to turn a raw RFC822 message into headers, bodies and attachments. Incoming mail has exactly one intake path: a DirectAdmin forwarder per address pipes each message to `parse.php`, which stores it through `EmailStorage::store()` with `OPTION_REJECT_UNKNOWN_RECIPIENT`. Nothing else receives or fetches mail — there is no shared mailbox and nothing polls one.
- **Frontend**: vanilla JS and plain CSS. No Node/npm, no TypeScript, no bundler, **no preprocessor and no build step**. Before editing anything under `assets/css/`, `assets/js/`, `partials/` or any public page, read `documentaion/REDESIGN_BRIEF.md` — §11 (CSS layering), §12 (hard rules) and §14 (SEO guardrails) are binding.
  - **Font**: a self-hosted Inter variable font in `assets/fonts/`, declared in `assets/css/mailshield-fonts.css`. No font CDN.
  - **Three stylesheets with a layering rule** (brief §11) — this is the rule most likely to be broken:
    - `assets/css/mailshield.css` — the design system: `--ms-*` tokens and `ms-`-prefixed components. **Never** shadows a Bootstrap class name.
    - `assets/css/mailshield-bootstrap.css` — the bridge. The **only** place allowed to restyle `.btn`, `.card`, `.form-control`, etc. Loaded last on Bootstrap pages.
    - `assets/css/style.css` — legacy. Retains its functional rules (modal widths, `#webhookList` flex behaviour, `.email-list` scrolling, hamburger geometry); its decorative rules are overridden by the bridge, **not deleted**.
  - **Marketing pages** (`index.php`, `temporary-email.php`) load only the fonts + `mailshield.css`: no Bootstrap, no Font Awesome, no jQuery. Icons are inline SVG. The one third-party script on them is Paddle.js, loaded by `index.php`'s plans card on production only, for the "From €x" price (see Retention and tier facts below).
  - **App and auth pages** (`inbox.php`, `register.php`, `pro_login.php`, `pro.php`, `pro_profile_page.php`, `client_agent_manage.php`, `pro_contact.php`, `faq.php`, `blog.php`) keep Bootstrap 5.3 + Font Awesome 6 + jQuery 3.7.1 from CDN and add the two Mail Shield stylesheets after `style.css`.
  - `assets/js/app.js` (class `TempMailApp`) drives the inbox; `assets/js/site-controls.js` is a no-op theme stub kept so the pages that still reference it do not break; a service worker lives at `assets/js/sw.js`. `assets/js/consent.js`, loaded by `partials/analytics.php`, shows the cookie consent notice and is the only thing that ever requests Google Analytics's `gtag.js` (see Frontend conventions below and brief §12.10).
  - Assets are cache-busted with `filemtime()`.
- **Deploy target**: traditional shared PHP hosting (see `.htaccess`, which blocks `.env|.log|.sql|.backup` and Docker files from being served). Docker is used for local/dev only.

## Configuration

`config.php` is the central entry point: it locates and loads a `.env.{environment}` file (searching several candidate directories, preferring a "secure" directory outside the webroot), populates `$_ENV`/`putenv`, builds the `$config` array (db, imap, app, cron, attachments), and opens the global `$pdo` connection. Every top-level script does `require_once 'config.php';` after `define('TEMPMAIL_APP', true);` — that define guards includes against direct access.

`.env.example` lists the core variables with placeholder values. adds Cloudflare's edge ranges and reads `CF-Connecting-IP`) — `getVisitorIp()` in `ip_utils.php` believes a forwarding header only when `REMOTE_ADDR` is one of these, otherwise it returns `REMOTE_ADDR`; use `getVisitorIp()`, never raw `REMOTE_ADDR`, for rate limits and `flagMaliciousActivity()`, see `tests/visitor_ip_test.php`. `ADMIN_USER_IDS` (see `log_viewer.php` below). `ADDRESS_COOLDOWN_MONTHS` (default 6) and `ADDRESS_COOLDOWN_MAX_PER_USER` (default 30) — the cool-off for removed personal addresses, see `address_cooldown.php`. `PRO_TRIAL_DAYS` (default 60, `0` = off) and `PRO_TRIAL_HASH_KEY` (≥ 32 characters, must never be rotated) — the 60-day Pro trial (epic #267), see the Pro tier entry below. `PII_ENCRYPTION_KEY` (≥ 32 characters; AES-256-GCM key, via sha256, for `email_enc`) and `PII_INDEX_KEY` (≥ 32 characters; HMAC key for the `email_hash` blind index) — users' email addresses at rest, see `pii_crypto.php` and "Email at rest" under Architecture. **Neither may ever be rotated without a re-encryption script**: a new encryption key makes every `email_enc` undecryptable, a new index key makes every `email_hash` lookup miss. It gates discovery only (the metadata documents and the 401 challenge); the OAuth endpoints themselves stay gated on `oauthAvailable()` as the earlier steps left them, so an existing token user is unaffected either way.

Never commit `.env.*` files, real secrets, or values for the vars above — `.gitignore` already excludes `.env.*`, `vendor/`, and generated client-agent secrets under `client/agent/`.

## Architecture

- **`config.php`** — env loading, `$config`, global `$pdo`. Required by nearly everything.
- **`index.php`** — the public marketing landing page **and** still the POST/AJAX action surface. The split is deliberate: after Redesign 07 the inbox reader moved to `inbox.php`, but the request handler stayed here because `assets/js/app.js` posts to the *relative* URL `'index.php'` (7 call sites), which resolves from `inbox.php` just as well — moving the handler would have meant touching every call. A request carrying a valid `?address=` on `index.php` 302-redirects to `inbox.php?address=…`, so old shared links keep working (brief §12.4). Everything above the landing markup is untouched legacy request handling — still the first place to look for the request-handling and DB-access conventions, and still a large file, but no longer the largest. Since #319, `create_personal`, `list_personal`, `delete_personal` and the signed-in branch of `generate` are thin wrappers: session authentication and Pro-gating (which need `$_SESSION`) stay here, everything else is `mailboxCreateSticky()` / `mailboxListAddresses()` / `mailboxDeleteSticky()` / `mailboxCreateTimed()` in `mailbox_service.php`, and each wrapper maps the result back to exactly the JSON the case answered before that file existed. `get_emails`, `refresh_emails`, `has_new_emails`, `get_email` and the anonymous (logged-out) branch of `generate` are untouched: they serve a logged-out visitor following a shared link too (`grantSessionAddressAccess()` / `hasSessionAddressAccess()`), a shape `mailbox_service.php`'s functions (written for a signed-in caller only) do not cover, and `get_emails` for a signed-in user still deliberately includes all of the account's addresses in one list rather than one address at a time. `case 'get_stats'` returns the **signed-in account's own** numbers (`getUserStats()` in `config.php`: emails in the inbox, received in the last 24 h, active addresses, storage against the mailbox quota) for the footer of `pro.php` / `inbox.php`, and answers `success: false` to a logged-out caller; the system-wide `email_stats` counters (`getStats()`) are shown only on the landing page, by `partials/landing/stats.php`. `emails_total` is no longer written by anything since #212 and is not displayed.
- **`mailbox_service.php`** (#319, part of epic #318 — the MCP server for Pro accounts) — the address and mailbox business logic factored out of `index.php` so a second entry point (a future `mcp.php`) can reuse it without duplicating ownership checks that would then drift apart. Every function takes `PDO $pdo` and `int $userId` explicitly, never reads `$_SESSION` and never echoes: it returns `['ok' => true, ...]` or `['ok' => false, 'error' => '<message>', ...flags]`. `mailboxListAddresses()` is the account's Sticky addresses (with abuse-guard quarantine state) plus its cool-off list and its one Timed address; `mailboxCreateSticky()` runs the same checks `create_personal` always has, in the same order (suspicious input, syntax, reserved names, taken, the cool-off holder, the cap of 10, the rate limit, the fail-closed forwarder, clearing the caller's own cool-off reservation); `mailboxDeleteSticky()` is `delete_personal`, including the cool-off reservation in the same transaction; `mailboxCreateTimed()` is the signed-in branch of `generate` — the account's one Timed address, its TTL from `address_ttl_days` when the account is Pro (clamped 1–7 days, 24 hours otherwise), replacing any existing Timed address in a transaction that only unlinks files and removes the old forwarder after the commit, so a failed new forwarder rolls back and keeps the previous address; it calls `saveNewAddressWithExpiry()` in `config.php` (the expiry passed as a parameter, not through `$GLOBALS['__custom_expires_at']` — `saveNewAddress()` keeps its old signature and global for its other caller, index.php's anonymous `generate` branch, and delegates to the new function). `mailboxDeleteTimed()` (#323) is the one function here with **no counterpart in `index.php`**: the site offers no way to delete a Timed address (it can only expire or be replaced), and the MCP `delete_address` tool is its only caller. It follows the order the replacement in `mailboxCreateTimed()` uses — `deleteStoredEmailsForTempEmail()`, the `pro_webhook_addresses` links and the `temp_emails` row in one transaction scoped by `pro_user_id` and `is_personal = 0`, then `unlinkAttachmentFiles()`, then the fail-open `deleteDirectAdminForwarder()` — and writes **no** cool-off reservation, because `address_cooldowns` holds released *Sticky* addresses and a Timed address' local part is free the moment it is gone. `mailboxCreationLimited()` is the address-creation rate limit (abuse_guard.php) moved out of index.php's `$creationLimited` closure, returning the verdict instead of echoing; the closure now just calls it and echoes the same JSON as before. `mailboxListMessages()` and `mailboxGetMessage()` are for the MCP tool surface (#322): unlike `index.php`'s own `get_emails`/`get_email`, they decide access by `temp_emails.pro_user_id = $userId` for either address kind, and answer the same "not found" whether an address/id belongs to someone else or does not exist at all, so nothing is revealed either way; they do not carry over `get_email`'s `cid:` body rewrite (tightly coupled to its own attachment lookups). `mailboxListMessages()` also returns an `attachment_count` per row (one correlated subquery), and `mailboxGetMessage()`'s attachments carry `size` (`file_size`) and `download_expires_at` next to the signed `download_url`, so a client can tell how large the file is and when its link stops working. `tests/mailbox_service_test.php` is the regression suite.
- **`inbox.php`** — the inbox reader, split out of `index.php`. Serves both a logged-in user and a logged-out visitor following a shared `?address=` link, which is why it is public but `noindex, nofollow`. Loads the app shell (`partials/nav.php`) and the Bootstrap/FA/jQuery dependencies plus the Mail Shield layers.
- **`temporary-email.php`** — the dedicated SEO page for the temporary/disposable-email keywords (brief §14). It exists so the site keeps the tempmail ranking it had without making the brand a TempMail site: it carries the tempmail-oriented `<h1>`, headings and body copy and links back to the landing page and to sign-up. Built directly on the public shell rather than from `partials/landing/`, with its own `ms-doc__section` sections.
- **`partials/`** — the shared page chrome:
  - `brand.php` — `ms_logo()` and `ms_shield_mark()` (both built on the internal `ms_shield_svg()`), returning inline SVG so the mark needs no icon font and inherits `currentColor`. Deliberately dependency-free — no `config.php`, no session, no DB — and every function is `function_exists`-guarded so a repeat `require` cannot redeclare them.
  - `public_head.php`, `public_nav.php`, `public_footer.php` — the marketing shell, driven by a `$msPage` array (`title`, `description`, `path`, `preload_font`, `og_type`, `jsonld`, `robots`) that each marketing page sets before requiring `public_head.php`. `public_head.php` emits the canonical/OG/Twitter tags, the JSON-LD block, the favicon and manifest links and the two marketing stylesheets, deriving the origin from `$config['email']['base_url']` — never from a literal.
  - `nav.php` — the **app** navigation (Bootstrap-classed markup that the bridge restyles). Signed-in accounts in `ADMIN_USER_IDS` also get an **Admin** link to `log_viewer.php`. Two contracts inline scripts depend on, and which must not be renamed: the `#proExpiryLine` element that the expiry status is written into, and `tm_nav_active()` plus the `navbar-link active` class it returns.
  - `landing/*.php` — one file per landing section, required in a fixed order by `index.php`: `hero`, `problem`, `how_it_works`, `addresses`, `temporary`, `automation`, `cleanup`, `external`, `stats`, `plans`, `cta`. `stats` is the system-wide numbers, server-rendered from `email_stats` and left out entirely when every figure is zero or the database is unreachable. Each is guarded by `if (!defined('TEMPMAIL_APP')) { http_response_code(403); exit; }`. The `public_*` shell partials carry no such guard — only guarded pages include them.
- **Legal pages** — `terms.php`, `privacy.php`, `refund-policy.php`, required by Paddle before domain approval and linked from `partials/public_footer.php`, `pricing.php` and `sitemap.php`. Each sets a `$msLegalDoc` array (title, lede, effective date, sections) and requires `partials/legal_page.php`, which renders the public shell; the facts they quote (company, contact address, trial length, quota, retention periods) come from `partials/legal_facts.php`, which reads `$config` (`$config['legal']`: env `LEGAL_ORG_NUMBER` and `LEGAL_VAT_NUMBER`, defaulting to the company's own numbers, and `LEGAL_CONTACT_EMAIL`, default `support@` on the mail domain). The privacy policy lists every data flow and third party the code has (Paddle, Google Analytics, user-configured integrations): adding a processor, tracker or cookie means updating it in the same change.
- **`sitemap.php`**, **`robots.txt`**, **`site.webmanifest`** — the crawler-facing metadata added by Redesign 21. `sitemap.php` is *generated*, not hand-written: it lists only the public indexable routes, takes `<lastmod>` from `filemtime()` of the file that serves each path, and derives its origin from `$config`; `.htaccess` rewrites `/sitemap.xml` to it. `robots.txt` disallows the private routes (`inbox.php`, `files.php`, `pro_*`, `client_agent_*`, `log_viewer.php`, `abuse_admin.php`, `parse.php`, `mcp.php` and its public URL `/mcp`, `oauth/`, `cron/`, `partials/`, `client/`, `documentaion/`) and is the **one deliberate exception** to "never hardcode the origin" — it is a static file, so its `Sitemap:` line hardcodes `https://manjo.me/sitemap.xml`, and it says so in a comment. `site.webmanifest` is minimal (name, theme colour, favicon); there is no offline app and no push.
- **`EmailStorage/`** — the single incoming-mail persistence boundary (epic #169, #190–#199). `EmailStorage.php` (`EmailStorage` class) is the service: `store(IncomingEmail $email, array $options = [])` owns recipient validation, the `temp_emails` + `pro_users.address_ttl_days` ownership/retention lookup, the opt-in duplicate rule, the transactional `stored_emails` INSERT, attachment persistence and the `emails_processed`/`attachments_processed` counters, returning a `StorageResult` (`stored`/`duplicate`/`rejected`/`failed`). `IncomingEmail.php`, `EmailAttachment.php` and `StorageResult.php` are the immutable contract types; `AttachmentStorage.php` writes one attachment's file + `email_attachments` row atomically and is the **only** writer of that table since #199 removed the parser's old `saveAttachments()`; `PostStorageWebhooks.php` is a registered post-storage consumer (`onStored()`; it calls `ImapProcessor::dispatchWebhooks()`), and `MailboxQuota.php` is a second post-storage listener (registered by `parse.php`): after each stored email it deletes the oldest mail in the same scope (the user account, or the address for anonymous addresses) until usage is at or below that scope's limit. The limit is tiered since #340 and resolved **per message**, never at construction: `$config['email']['quota_bytes_pro']` (default 100 MB, env `MAILBOX_QUOTA_PRO_BYTES`, falling back to the old `MAILBOX_QUOTA_BYTES`) for an account `proUserIsPro()` calls Pro — the 60-day trial included — and `quota_bytes_free` (default 10 MB, env `MAILBOX_QUOTA_FREE_BYTES`) for a Regular account or an anonymous address. An account that drops to Regular (a trial or a plan ending) is therefore trimmed to the Free limit by its next message, oldest first; an upgrade just stops trimming. A tier lookup that fails falls back to the **Pro** limit and logs a WARNING with the `user_id`, because a listener may never delete a paying account's mail over a lookup error. The intake path below (`parse.php`) is the only caller of `store()` — **no other code writes `stored_emails` or `email_attachments` for ingestion**, the exceptions being cleanup/deletion/read-side statements listed in `documentaion/EMAIL_STORAGE_ARCHITECTURE.md` §3.1. Mail is stored via this service, not by the caller. `documentaion/EMAIL_STORAGE_ARCHITECTURE.md` is the architecture map, `documentaion/EMAIL_STORAGE_API.md` the contract.
- **`php_imap_processor.php`** (`ImapProcessor` class) + **`MailParser.php`** (`MailParser` class) — the class name is historical: this was the IMAP intake, which was removed in #212. What is left holds only Pro webhook dispatch — `dispatchWebhooks()` queues and `dispatchDelivery()` sends — and, like the `TEMPMAIL_*` identifiers, the name is deliberately not changed. `MailParser` is a parser only: it takes no PDO and writes nothing, its old `saveAttachments()` having gone in #199, and `parse.php` is what calls it. Pro webhooks are not dispatched by the intake: they run from the service's post-storage listener, which calls `dispatchWebhooks()` to queue them and then `deliverNow()` to send them straight away (at most `WEBHOOK_IMMEDIATE_LIMIT`, default 5, per email; `WEBHOOK_DELIVER_IMMEDIATELY=false` turns this off). `cron/process-webhook-deliveries.php` is the retry path for whatever fails, with backoff; `dispatchDelivery()` claims a row with a short `next_attempt_at` lease first, so the pipe and the worker never send the same delivery twice.
- **`parse.php`** — CLI-only entrypoint for the DirectAdmin pipe-forwarder mail intake (#34): DirectAdmin pipes each incoming message to `php parse.php`, which reads the raw RFC822 message from `php://stdin`, derives the recipient's temp-address local part from `argv[1]`/`LOCAL_PART`/`RECIPIENT` (see the script's header comment — this hasn't been confirmed against the live Exim config), validates it with the same regex as everything else here, looks up the `temp_emails` row, parses with `MailParser::parseRawMessage()` and **stores via the Email Storage service** (`EmailStorage::store()` with `OPTION_REJECT_UNKNOWN_RECIPIENT`, #193) — it performs no INSERT of its own and no longer calls `dispatchWebhooks()` itself, because the webhook consumer is a post-storage listener registered on the service. Rejects (non-zero exit) on invalid/unknown/expired recipients so the MTA can bounce. Messages larger than `$config['email']['max_message_bytes']` (default 10 MB, env `MAX_MESSAGE_BYTES`) are rejected (exit 1, bounce) without being parsed — after the recipient lookup, so the abuse guard can count their bytes against the address. Between the lookup and the parse sits the abuse guard (see "Abuse guard" below): every message to a known address is counted, a message to a quarantined address is dropped with exit 0 (never bounced — the sender is usually forged), and the one that crosses a limit quarantines the address and is dropped the same way; attachments beyond 10 (and inline images beyond 50) per message are left out of the stored copy. Refuses to run outside CLI SAPI. Its exit codes are the intake contract: `0` stored; `1` permanent rejection (invalid, unknown or expired recipient, empty input), with the reason printed on stderr so Exim bounces; `75` temporary failure (DB unreachable, storage failure, uncaught exception), with nothing printed so Exim defers and retries. `config.php` honours `TEMPMAIL_PIPE_INTAKE`, which only `parse.php` defines, by exiting 75 silently on a DB connection failure. The webhook gap described here previously (every Pro webhook, Pushover included, silently stopped firing for switched-over addresses when `DA_FORWARDER_ENABLED` was flipped on in production) is what #188 fixed and #196 moved onto the shared listener.
- **`DirectAdminClient.php`** (`DirectAdminClient` class) — isolated API client for DirectAdmin's `CMD_API_EMAIL_FORWARDERS` endpoint (`createForwarder($alias, $destination)` / `deleteForwarder($alias)`). It creates and removes the per-address forwarder that pipes mail into `parse.php`, the one intake path for incoming mail. Configured via `$config['directadmin']` (`DA_HOST`, `DA_USER`, `DA_API_KEY`, `DA_DOMAIN`, `DA_FORWARDER_DESTINATION`, `DA_FORWARDER_ENABLED` — on by default in production, off by default elsewhere; an explicit value always wins). `config.php`'s `createDirectAdminForwarder($alias)` / `deleteDirectAdminForwarder($alias)` wrap the client — creation is fail-closed (an address whose forwarder cannot be created is not created, and the user is told); deletion stays fail-open (a failed delete logs `ERROR` since it can leave an orphaned forwarder) — and are called from address creation/deletion in `index.php` and expiry cleanup in `cron/cleanup.php` (see those entries). `php check_directadmin_client.php` runs a DB/network-free CLI smoke test of construction and alias validation.
- **`cron/`** — scheduled jobs: `cleanup.php` (expire old addresses — `cleanupExpiredAddresses()`/`cleanupExpiredProUsers()` also call `deleteDirectAdminForwarder()` for each removed address, see `DirectAdminClient.php` entry above; `cleanupInactiveRegularAccounts()` warns then permanently deletes long-inactive `account_type='regular'` accounts — never Pro accounts — based on `COALESCE(last_login_at, created_at)` against `REGULAR_INACTIVITY_WARN_DAYS`/`REGULAR_INACTIVITY_DAYS`, see `documentaion/ACCOUNT_TIERS.md` §6.2), `process-webhook-deliveries.php`, `requeue-webhook-delivery.php`, `rotate_signing_keys.php`, `send-digests.php`, `abuse-guard.php` (every minute, see the Abuse guard entry). The cleanup job also runs the small sweeps its own file defines: expired "Stay signed in" devices (`cleanupExpiredRememberTokens()`), MCP access tokens revoked or expired more than 30 days ago plus those whose account is gone (`cleanupExpiredMcpTokens()` → `mcpTokenCleanup()`, which since #331 step 4/6 keeps a row whose OAuth refresh token is still valid), and — run after that one, so a client whose revoked grant was just removed becomes sweepable — authorization codes older than a day and OAuth clients with no token row and no activity for 30 days (`cleanupExpiredOauth()` → `oauthCodeCleanup()` / `oauthClientCleanup()`), all three skipping silently until their migration has run.
- **Pro tier** — `pro_login.php` / `pro_auth.php` (magic-link auth), `pro.php` / `pro_profile.php` / `pro_profile_page.php` (dashboard/settings), `pro_feed.php` (RSS), `pro_contact.php`, `pro_logout.php`. (The Buy Me a Coffee webhook, `bmac_handler.php`, was removed: it was never called in production.) There are **two kinds of RSS feed**, both Pro-only, both served by `pro_feed.php` at the same URL shape and told apart by which table the token resolves in: the **account-wide** feed (`pro_users`, covering all addresses) and the **per-address** feeds (`temp_emails`, one personal address each — the plaintext column and its unique key added by `migrate_address_feed_tokens.php`, see Commands above). Since #315 the token itself is a bearer credential kept at rest like `pii_crypto.php`'s `email_enc`/`email_hash`: both tables also carry `feed_token_hash` (plain SHA-256 of the token — unkeyed, because the token is already 256 random bits — UNIQUE, added by `migrate_feed_token_encryption.php`) and `feed_token_enc` (`webhookSecretEncrypt()`/`webhookSecretDecrypt()` under `WEBHOOKS_KEY`, see `feed_token.php`). `pro_feed.php` looks a token up by `feed_token_hash` only, never the plaintext column, so lookup keeps working even without `WEBHOOKS_KEY`; minting or regenerating a token (`feed_get_token` / `feed_regenerate` / `address_feed_get_token` / `address_feed_regenerate` in `pro_profile.php`) writes the hash/enc pair and clears the plaintext, and refuses (fail closed) without `WEBHOOKS_KEY` rather than falling back to plaintext; showing an existing token decrypts `feed_token_enc` and answers `success:false` (offering Regenerate) if that fails, logging an ERROR with ids only, never a token. `pro_profile_page.php` surfaces both: the account feed in its own card, the per-address feeds as an RSS button on each row of the Personal addresses card, whose token is fetched lazily on first expand through the Pro-gated `address_feed_get_token` / `address_feed_regenerate` / `address_feed_disable` actions in `pro_profile.php`. `list_personal` in `index.php` returns only a boolean `feed_enabled` (`feed_token_hash IS NOT NULL`), never the credential, because that action is deliberately not Pro-gated — a degraded account must still be able to see and delete its addresses. Webhook routing is per hook and per address (epic #251): `pro_webhook_addresses` (added by `migrate_webhook_addresses.php`, see Commands above) links one hook to the personal addresses it fires for, `pro_webhooks.include_temporary` is one switch covering all of the user's temporary addresses, and `temp_emails.hooks_paused` is the per-address pause, which silences an address without dropping its links. `ImapProcessor::dispatchWebhooks()` resolves the destination address (the recipient the intake resolved from the message headers and saved on `stored_emails.to_address`) through `hooksForDestination()`: a personal address queues exactly the user's active hooks linked under it, or nothing at all while paused; a temporary address queues the user's active hooks with `include_temporary = 1`; a paused hook (`filter_mode != 'all'`) never queues, whatever it is linked to. Every hook kind is routed the same way — Pushover gets no special case — and dispatch is fail-closed: anything unproven (a missing row, an address not owned by the user being dispatched for, a lookup failure, or the routing schema itself being absent) queues nothing, and a missing schema logs a WARNING naming `migrate_webhook_addresses.php`. New addresses and new hooks start unlinked, so they start silent. The Pro-gated `webhook_set_addresses` action replaces a hook's whole address set, and `address_hooks_pause` / `address_hooks_resume` flip one address' pause; both resolve ownership with id + `pro_user_id` + `is_personal = 1` in one query, and the pause pair is never a credential — the links themselves stay in `pro_profile.php`. There are no foreign keys by design, so the deletion paths that touch neither table (`cleanupExpiredAddresses()`, `cleanupExpiredProUsers()` and the account deletion in `pro_auth.php`) can leave link rows behind; `cleanupOrphanWebhookAddressLinks()` in `cron/cleanup.php` sweeps those. `temp_emails.pushover_enabled` remains in the schema but is unused: #251 step 6 retired the per-address Pushover opt-in, and the column is kept only so a rollback of the code stays possible. `pro_users` holds both Regular (free) and Pro accounts — the account type lives in the `account_type` column (`'regular'` or `'pro'`, added/backfilled by `migrate_account_types.php`, see Commands above) and entitlement is always decided by `proUserIsPro($userId)` in `config.php` (never re-check `pro_expires_at` directly elsewhere); `proUserAccountType($userId)` returns the raw `account_type`. Both fall back to the legacy "`pro_expires_at` is NULL or in the future" rule when the migration hasn't run yet, so deploy order doesn't matter. `php check_account_tiers.php` is the CLI smoke test for this data model. Login itself is tier-neutral: magic link and password login both let in any account with `email_verified_at` set (falling back to "treat as verified" when that column doesn't exist yet), regardless of Regular/Pro status — Pro-only gating happens on individual features (#54–#56), not at the login gate. All three login paths (magic link, password, password+2FA) record `last_login_at = NOW()` via `recordProUserLogin()` in `pro_auth.php`, fail-open on error. `pro_trial.php` records a hashed, normalised address in `pro_trial_claims` on an address' first proof (first verification, voucher account creation, confirmed email change), a table with no link to `pro_users` so a claim survives account deletion; only first verification (`pro_login.php`) grants the 60-day trial itself. The claim rows are swept after five years by `cleanupExpiredTrialClaims()` in `cron/cleanup.php`. See `documentaion/ACCOUNT_TIERS.md` §10.
- **Stay signed in** (`pro_remember.php`, table `pro_remember_tokens` from `migrate_remember_tokens.php`) — the PHP session cookie still dies with the browser and the session file with the host's `gc_maxlifetime`, which signed mobile users out whenever the OS closed the browser in the background. A user can instead keep a device signed in for 1, 7 or 30 days: chosen on `pro_login.php` (carried through the magic link as `&stay=N` and through `pending_2fa` until the code is verified) or on `pro_profile_page.php` (Security → Stay signed in, which also lists and removes devices). The device gets an `ms_stay` cookie (`selector.validator`, only sha256 of the validator stored, same scheme as the 2FA trusted-device cookie); `proSessionEndIfSuspended()` calls `proRememberRestoreSession()` first, so every page that trusts the session re-creates it from a valid cookie — rotating the validator (the previous one stays valid for 120 s, for the parallel requests a resumed page fires) and sliding the expiry, never past 90 days after the sign-in. A token is created only after a complete sign-in; a suspended or deleted account is never restored; sign-out removes the device's token, and a password or email change (and their undo links) and account deletion remove all of them. Everything is fail-open: without the table, sign-in works exactly as before.
- **MCP access tokens** (`mcp_tokens.php`, table `mcp_access_tokens` from `migrate_mcp_tokens.php`, epic #318 step 2) — the credential an MCP client sends as `Authorization: Bearer …`. There are two ways to get one and they are the same row: a **manual token** the user creates on the Connected apps card, and an **OAuth access token** the flow in `oauth_server.php` (epic #331) issues after the user approves an app. The OAuth row additionally carries `oauth_client_id`, `refresh_token_hash`, `refresh_expires_at`, `grant_created_at` and the rotation columns, which is what makes it a grant as well as a token — but it is minted with `mcpTokenGenerate()` and stored with `mcpTokenHash()` exactly like a manual one, never a fork of that code, so `mcpTokenResolve()` decides on it with no OAuth-specific branch. Every other way into an account (a magic link, a password with optional 2FA, the `ms_stay` cookie) is a browser session and no client can use it. A token is `msk_` + 64 lowercase hex characters from `random_bytes(32)`; only `hash('sha256', $token)` is stored — unkeyed, exactly like `feed_token_hash`, because the token is already 256 random bits — and it is shown **once**, at creation: nothing can display it again, so a lost token is revoked and replaced. `mcpTokenResolve()` is the whole access decision: it validates the format before any query, then resolves to nothing for a revoked or expired row, an account that is no longer Pro (`proUserIsPro()`), a suspended one (`proUserIsSuspended()`) or a missing table, and it writes `last_used_at` at most once a minute. An account holds at most 10 active tokens (expired ones do not count, since they are swept later); the 11th is refused, never silently dropped to make room. Tokens are revoked (`revoked_at`), not deleted, and the removal paths are the same ones `pro_remember.php` clears devices on — a password or email change and both undo links, an account deletion, an admin suspension in `abuse_admin.php` and an inactive account's removal in `cron/cleanup.php` all call `mcpTokensRevokeAllFor()`, which is fail-open so a missing table can never undo the password change that got us there. The Pro-gated `mcp_token_create` in `pro_profile.php` returns the token in its answer; `mcp_token_list` and `mcp_token_revoke` are deliberately *not* Pro-gated, because revoking is how a credential is taken away and a degraded account must still be able to do it. The "Connected apps" card on `pro_profile_page.php` (Security) is the UI: since #331 step 4/6 it has two groups — **Connected apps** (the OAuth grants, app name, access, connected and last-used dates, Revoke) and **Access tokens** (the manual ones: name, access, expiry, the one-time token with a copy button, Revoke), both filled from the one `mcp_token_list` answer; creating a manual token is Pro-only, and without the table the card says the feature is not available yet. The "How to connect" help is the same card's last block, and since #331 step 6 it follows `oauthDiscoveryEnabled($pdo)`: with OAuth on it leads with "Add `<base_url>/mcp` in your app and sign in when it asks" (Claude.ai, a Claude Desktop custom connector, Claude Code) and keeps the two copyable examples as the token route for a client that only takes a header; with OAuth off it says tokens and nothing else, because a sign-in no client can perform is a claim the code does not back (brief §9). The endpoint in that copy is `rtrim($config['email']['base_url'], '/') . '/mcp'`, never a literal, and the card's description and the grants empty-state sentence are gated the same way. See the "Connected apps: grants and tokens" entry below. Only the token id and `user_id` are ever logged. `cron/cleanup.php` sweeps revoked and expired rows after 30 days plus rows whose account is gone (`mcpTokenCleanup()`); `check_mcp_tokens.php` audits the table. `tests/mcp_tokens_test.php` is the regression suite.
- **The MCP endpoint** (`mcp.php` + `mcp_tools.php`, epic #318 step 3/6, #321) — the one HTTP endpoint an MCP client talks to. Users are given `<base_url>/mcp`; `.htaccess` rewrites `^mcp/?$` to `mcp.php` and copies the request's `Authorization` header into `HTTP_AUTHORIZATION` (Apache with CGI/FastCGI strips it before PHP starts; `mcp.php` reads `HTTP_AUTHORIZATION` and `REDIRECT_HTTP_AUTHORIZATION`). It deliberately does **not** use `CGIPassAuth`: that is a directive `AllowOverride` can forbid, and a forbidden directive answers 500 for the whole tree, while mod_rewrite is already in use and proven here. **Transport**: Streamable HTTP restricted to what shared hosting serves — POST only (every other method, `GET` included, is 405 with `Allow: POST`; there is no SSE stream and no `Mcp-Session-Id` is ever minted or echoed), `application/json` in and out, one JSON-RPC 2.0 request or notification per HTTP request, a notification answered 202 with no body, batches refused, `Cache-Control: no-store`, and no session, cookie or CSRF token anywhere on the path. **Protocol revision**: `MCP_PROTOCOL_VERSION` is pinned to `2025-11-25` — deliberately *not* the newest revision. MCP 2026-07-28 removed the `initialize` handshake (the version travels per request in `_meta`, `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name` must be validated against the body, and a `server/discover` RPC is required), while this endpoint is the handshake shape: `initialize` → `notifications/initialized` → requests. 2025-11-25 is the last revision that has it, and it is what a current dual-era client falls back to — Claude Code opens with a `server/discover` probe and treats any non-DiscoverResult answer (this endpoint's -32601 included) as a legacy server, then asks for `2025-11-25` by name. Answering a modern version while speaking the handshake would advertise what the endpoint does not implement and leave the client nothing to fall back to. A request carrying a different `MCP-Protocol-Version` is refused with 400. (That revision's *authorization* section is a separate question — it now prefers OAuth Client ID Metadata Documents over the RFC 7591 dynamic registration this server implements, and asks for a `scope` in the 401 challenge; see the note at the end of the OAuth client registration entry.) **Order of checks**, stopping at the first failure: method and `Content-Type` (415), protocol version (400), `Origin` — absent, or this site's own origin from `$config['email']['base_url']` compared scheme+host+port, never the request's `Host`, else 403, the specification's DNS-rebinding defence — then the Bearer token through `mcpTokenResolve()` (missing/malformed/unknown/revoked/expired → 401 with `WWW-Authenticate: Bearer realm="Mail Shield"` — since #331 step 5/6 that challenge also carries `resource_metadata="<base_url>/.well-known/oauth-protected-resource"` and the missing-token JSON-RPC error names both routes to a credential — the client's own sign-in flow, or an access token under Profile → Security → Connected apps — but only while OAuth discovery is on, see the discovery entry below; the resolve's reason argument is for the two cases that are *not* a credential problem: an account that has lost Pro or is suspended → 403 with a JSON-RPC error naming Pro, unchanged and never carrying a challenge), then the per-token rate limit (`abuseMcpTokenRateLimit()` in `abuse_guard.php`, `mcp_token` scope, 1-minute buckets read over both a minute and an hour window, subject = the token id so two clients of one account do not spend each other's budget, `MCP_RATE_PER_MINUTE`/`MCP_RATE_PER_HOUR`, over it → 429 with `Retry-After`; fail-open like the rest of the guard), then the body (64 KB cap → 413, parse error → -32700, batch → -32600), then dispatch: `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`, anything else -32601. **Tools** live in `mcp_tools.php`: `mcpToolRegistry()`, each entry naming its `scope` (`read`/`write`), and `mcpToolsForScopes()` filters both `tools/list` and `tools/call` so the two cannot drift; a token's scopes are `read` or `read,write`, and a `read` tool is the only kind either scope may call. #321 shipped the registry empty; **#322 registered the three read tools**, each with the `readOnlyHint` annotation: `list_addresses` (the account's Sticky and Timed addresses with their expiry and abuse-guard pause state, plus the Sticky count and the cap of 10), `list_messages` (one address' unexpired mail, newest first, as plain-text previews with an attachment count) and `get_message` (one message's sender, subject, received time, plain-text body and signed attachment links). All three take the user id from the token, never from the request, and defer every ownership decision to `mailbox_service.php` (#319); the address may be a local part or a full address, but only one on our own domain is looked up, and another account's address, a missing one and a foreign domain all answer "Address not found", while another account's message, a missing id and an expired one all answer "Message not found" — the answers must not be distinguishable, or ids and local parts could be enumerated. **#323 added the three write tools**, all `scope => 'write'` (so only a `read,write` token sees them, and `tools/call` refuses the name for a `read` token even if the client kept it): `create_sticky_address` (`{ local_part }` → the full `address`, `kind: "sticky"`, `expires_at: null`; it is `mailboxCreateSticky()`, so every rule the site applies — reserved names, syntax, taken, the cool-off holder, the cap of 10, the shared `personal_user` rate limit, the fail-closed forwarder — answers in the site's own words, and `destructiveHint` is `false` because it deletes nothing); `create_timed_address` (`{ replace_existing? }`, `destructiveHint: true`; an account has only one Timed address, so when one already exists and `replace_existing` is not `true` the call is refused *naming that address and saying its mail would be deleted* — checked before the shared `gen_user` rate limit so a call that can do nothing spends no budget — and the successful answer adds `replaced`, the old address or `null`); and `delete_address` (`{ address, confirm }`, `destructiveHint: true`; without `confirm: true` it is refused and says which address and how much would go, and ownership is decided *before* that gate so the gate cannot be used to probe which local parts exist — an address that is not this account's answers "Address not found" either way). A Sticky deletion goes through `mailboxDeleteSticky()` and the answer carries `reserved_until` (read back from `address_cooldowns`); a Timed one goes through the new `mailboxDeleteTimed()`, whose only caller this is, and `reserved_until` is `null`. Both are `mailbox_service.php` decisions; the handlers only add the two "nothing is deleted by accident" gates. The site's inbox gets no delete button for a Timed address. The address of each create/delete is logged by the service (INFO with `user_id`), as a service-domain address may be. **Untrusted content**: subjects, senders and bodies come from outside senders but reach a language model, so a tool's successful answer carries its fields as `structuredContent` (JSON) plus a `text` content item stating the same fields (`mcpToolResult()`, nothing added in Mail Shield's voice), every description says the content is untrusted data and never instructions, and message bodies are **plain text only** — `body_text`, or `emailHtmlToText()` of `body_html`, cut at 20 000 characters with `truncated: true`; no HTML body, no raw headers and no `cid:` rewriting ever leaves the tool. A handler follows `mailbox_service.php`'s shape and a handler *failure* is an ordinary result with `isError: true`, not a protocol error. **Logging**: one INFO line per tool call with `user_id`, token id, tool name and outcome, and a WARNING with `getVisitorIp()` for a rejected `Origin`, a malformed credential and a rate-limit hit; the token, the request body and message content are never logged. `tests/mcp_endpoint_test.php`, `tests/mcp_read_tools_test.php` and `tests/mcp_write_tools_test.php` are the regression suites; `robots.txt` disallows `/mcp.php` and `/mcp`.
- **OAuth client registration** (`oauth_server.php` + `oauth_register.php`, epic #331 step 1/6) — the first, deliberately inert step of the OAuth 2.1 work that will let a client (Claude.ai, Claude Code) connect to `/mcp` without a copy-pasted token. `migrate_oauth.php` creates `oauth_clients` (one row per dynamically registered **public** client: a 32-hex `client_id`, the `client_name`, the `redirect_uris` JSON array, `created_at`, `last_used_at`, and `registered_ip_hash` — a keyed sha256 of the registering IP, never the raw address) and `oauth_authorization_codes` (pending single-use codes, stored only as a sha256 `code_hash`), and widens `mcp_access_tokens` with nullable `oauth_client_id`, `refresh_token_hash` (unique), `refresh_expires_at`, `grant_created_at`, `rotated_refresh_hash` and `rotated_at` plus an `(oauth_client_id, pro_user_id)` index — so a later step's OAuth access token is an ordinary row that `mcpTokenResolve()` already decides on; every manual token leaves those columns NULL. `oauth_server.php` is the shared library (`oauthAvailable()`, `oauthClientRegister()`, `oauthClientFind()`, `oauthClientCount()`, redirect-URI validation, and the random-id / `hash('sha256', …)` helpers the later steps reuse; step 2/6 added the grant functions to it, see the next bullet); it takes an explicit PDO, never touches `$_SESSION` and never echoes, like `mailbox_service.php` — which is also why `tests/oauth_register_test.php` runs it on SQLite. The endpoint is `/oauth/register` (`.htaccess` rewrites `^oauth/register/?$` to `oauth_register.php`), RFC 7591: POST `application/json` only, one JSON object of at most 8 KB; it accepts `client_name` (trimmed, control characters stripped, ≤ 64 characters, default "Unnamed app"), `redirect_uris` (1–5), `grant_types` (⊆ `authorization_code`, `refresh_token`), `response_types` (`code` only), `token_endpoint_auth_method` (`none` only) and `scope` (informational, not stored), ignores unknown fields, and answers **201** with `client_id`, `client_id_issued_at`, `redirect_uris`, `client_name`, `grant_types`, `response_types` and `token_endpoint_auth_method: "none"` — no client secret is ever issued. A redirect URI must be absolute, without fragment or userinfo and ≤ 512 characters, `https` for any host or `http` only for the loopback hosts `127.0.0.1`, `[::1]` and `localhost`, and for a custom scheme (`cursor://`, `vscode://`) have a non-empty host or path and not be `javascript:`, `data:`, `file:` or an http(s) look-alike; a later step matches them by **exact string**. Every failure is an RFC 6749 §5.2 JSON error body (`invalid_redirect_uri` / `invalid_client_metadata`; 405/415/413/400 for the transport cases), and before the migration the endpoint answers **503 `temporarily_unavailable`** (fail closed — `oauthAvailable()` is false). Abuse limits go through `abuse_guard.php` (fail-open, like the rest of the guard): per-IP registrations per hour and per day and the global ceiling on stored clients, over either → **429** with `Retry-After`, the per-IP subject being `oauthIpHash()` — the keyed hash, never the raw address (no key configured ⇒ the per-IP limit simply does not apply). Logging is one INFO line with the `client_id` and the client name plus a WARNING with `getVisitorIp()` when a limit is hit; a redirect URI is never logged. Nothing on the site links to this route — a client reaches it through `registration_endpoint` in the authorization-server metadata document (step 5/6, below), which is served only while `OAUTH_ENABLED` is on; `robots.txt` disallows `/oauth/`. `check_oauth.php` audits the schema and `tests/oauth_register_test.php` is the regression suite.
  **On the pinned revision's authorization section** (`MCP_PROTOCOL_VERSION` is `2025-11-25`): that revision moved to **OAuth Client ID Metadata Documents** (`draft-ietf-oauth-client-id-metadata-document-00`) as the preferred way for a client to identify itself, with RFC 7591 dynamic client registration demoted to a **MAY** "included for backwards compatibility" — which is the route this endpoint implements. A client that supports CIMD looks for `client_id_metadata_document_supported` in the authorization-server metadata, does not find it here, and falls back to `registration_endpoint`, so the flow still completes and nothing about epic #331 is non-compliant. The revision also asks servers to put a `scope` parameter in the 401 challenge (RFC 6750 §3, a SHOULD, for step-up authorisation) and to answer an insufficient scope at runtime with 403 + `error="insufficient_scope"`; `oauthWwwAuthenticate()` sends neither, and the endpoint has no per-tool scope split to trigger the latter — a tool a token's scope does not cover is refused as an ordinary tool error instead. Neither CIMD nor the challenge `scope` is part of epic #331.
- **The OAuth token endpoint and revocation** (`oauth_token.php` + `oauth_revoke.php`, epic #331 step 2/6, on `oauth_server.php`) — the exchange a client makes once a user has approved it. The code it exchanges is minted by the authorization endpoint (step 3/6, above). `/oauth/token` (`.htaccess` rewrites `^oauth/token/?$`) is POST `application/x-www-form-urlencoded` only, ≤ 8 KB, with `Cache-Control: no-store` and `Pragma: no-cache` on every answer; `/oauth/revoke` (rewrite `^oauth/revoke/?$`) is POST only. Every failure is an RFC 6749 §5.2 `{"error", "error_description"}` body: **400** for `invalid_request`, `invalid_grant`, `invalid_scope` and `unsupported_grant_type`, **401** only for `invalid_client`, **405** with `Allow: POST` for another method, and **503 `temporarily_unavailable`** when the migration has not run (fail closed, like `/oauth/register`). **`grant_type=authorization_code`** requires `code`, `redirect_uri`, `client_id`, `code_verifier` and the `resource` the authorization bound, when it bound one (RFC 8707; a resource the authorization never named is ignored). An unknown or malformed `client_id` is `invalid_client`; **everything else — an unknown code, an already used one, an expired one, another client's, a different `redirect_uri`, a wrong verifier, an account that is no longer Pro and a suspended one — is the same `invalid_grant`**, so a client cannot use the answers to probe which codes exist. PKCE is S256 only (`base64url(sha256(verifier))` through `hash_equals`, verifier 43–128 characters of `[A-Za-z0-9-._~]`), which is what the 43-character `code_challenge` column holds. The code is consumed by the same atomic `UPDATE … WHERE used_at IS NULL` that claims it, inside the transaction that creates the grant, so a failed exchange never burns a code; a **second use revokes what the code granted** (RFC 6749 §4.1.2) — under one-grant-per-(user, client) that is exactly the live grant for the pair, found by `oauth_client_id` + `pro_user_id` rather than a new column. **`grant_type=refresh_token`** requires `refresh_token` and `client_id`, rotates unconditionally (new access token, new refresh token, the consumed one kept as `rotated_refresh_hash`), and **presenting that rotated token revokes the whole grant** — the re-use detection OAuth 2.1 asks for; `scope` can narrow and never widen (`invalid_scope`), and a revoked or expired grant, an account that lost Pro and a suspended one are all `invalid_grant`. The answer is `access_token` (`msk_…` from `mcpTokenGenerate()` — **an OAuth access token is an ordinary `mcp_access_tokens` row, so `mcpTokenResolve()` needed no change at all**, which `tests/oauth_token_test.php` verifies rather than assumes), `token_type: "Bearer"`, `expires_in: 3600`, `refresh_token` (`msr_` + 64 hex, only its sha256 at rest, 90 days sliding from every rotation) and `scope` in the wire form `mcp:read` / `mcp:read mcp:write` — `oauthScopeSetFromExternal()` and its neighbours are the only translation to and from the stored `read`/`read,write`, and `write` always implies `read`. The row is named after the client and carries `oauth_client_id`, `scopes`, `expires_at` (now + 1 h) and `grant_created_at`; `oauth_clients.last_used_at` is written at most once an hour, on a successful exchange. **One grant per (user, client)**: authorising again replaces that pair's rows, revoked ones included. An account holds at most **10** grants — the 11th authorisation is refused at consent time in 3/6 and again here as `invalid_grant` — which is a separate cap from #320's ten *manual* tokens, though both count against the "Connected apps" list because both are rows in the same table. **`/oauth/revoke`** (RFC 7009) revokes the grant when the token is that client's access **or** its live refresh token, and **always answers 200 with an empty body**, whatever happened — no oracle. Because every statement it makes requires `oauth_client_id` to match a registered client, a manual token (`oauth_client_id` NULL, every token the profile created) and another client's token are unreachable from it. Abuse limits go through `abuse_guard.php` (fail-open): per-IP exchanges per hour and per day (`OAUTH_TOKEN_IP_HOUR`/`OAUTH_TOKEN_IP_DAY`, 60/300), keyed on `oauthIpHash()` — never the raw address — over either being **429** with `Retry-After`; `/oauth/revoke` is deliberately *not* limited, because answering 200 to everything is the point of it. Logging is one INFO line per exchange with `user_id`, token id, `client_id`, grant type and outcome, plus a **WARNING with `getVisitorIp()`** when a code or a refresh token was presented twice (the line an operator needs when a grant is revoked under someone's feet). The access token, the refresh token, the code and the verifier are never logged, in any form, and `oauth_server.php` logs nothing itself — the endpoint does. `tests/oauth_token_test.php` is the regression suite.
- **The OAuth authorization endpoint and consent page** (`oauth_authorize.php`, epic #331 step 3/6, on `oauth_server.php` + `after_login.php`) — the one step where a human decides. `/oauth/authorize` (`.htaccess` rewrites `^oauth/authorize/?$`) answers **GET** with the consent page and **POST** with the decision; anything else is 405 with `Allow: GET, POST`. The request is never carried by the form: GET validates it and stores the validated parameters in the session, and POST **re-validates that same stored request** — the browser posts only the CSRF token and the scope the user picked, so there is no hidden `client_id`, `redirect_uri`, challenge or scope to tamper with. **Validation order** (`oauthAuthorizeRequestValidate()`): (1) a `client_id` that names no registered client (a malformed one is refused before any query) or a `redirect_uri` that is missing or not an **exact** string match of one the client registered is **fatal** — the endpoint renders an error page on our own origin and never redirects (RFC 6749 §4.1.2.1; redirecting either would be a redirect gadget); (2) from there every error goes back to the proven redirect URI as `error=…&state=…&iss=…` with `iss` our own origin (RFC 9207, from `$config['email']['base_url']`) — `invalid_request` (missing `response_type`, missing or non-43-character-base64url `code_challenge`, `code_challenge_method` other than `S256` — **plain PKCE is refused, never downgraded** — a `resource` that is not the canonical `<base_url>/mcp` (RFC 8707), a `state` over 512 characters), `unsupported_response_type` (anything but `code`) and `invalid_scope` (a scope outside the two MCP scopes; **no scope at all means read**). **Eligibility**: the account must be signed in — a signed-out visitor is sent to `pro_login.php` and the request waits in the session (see the after-login entry below, which is why `pro_login.php` has a "return to" mechanism at all) — must be Pro (`proUserIsPro()`) and must have room for one more grant (`oauthGrantExists()` lets a client the account already connected re-authorise past `OAUTH_GRANT_MAX_PER_USER`; a genuinely new eleventh app gets a 403 pointing at Connected apps). A suspended account is signed out by `proSessionEndIfSuspended()` and lands in the signed-out branch, exactly as everywhere else. **CSRF** is an HMAC over the stored request's signature under a per-session secret, so a token is bound to this session **and** to this exact request: another session's token, another request's token and a replayed decision are all refused, and the pending entry is consumed by the first answer. **The consent page** is the auth shell in the app style group (Bootstrap + the two Mail Shield layers, brief §11), `noindex, nofollow`, with **no analytics partial**, `X-Frame-Options: DENY` and CSP `frame-ancestors 'none'` so the two answers cannot be clickjacked; the app's name is attacker-controlled, so it is escaped, quoted and explicitly labelled as the name the app gives itself, with the redirect host beside it; the two answers are radios so the narrower grant starts checked, and the notice says plainly that what the app reads goes to whoever runs it. **On Allow** `oauthAuthorizationCodeCreate()` mints the code (32 random bytes as hex, 60 s, **only its sha256 stored**) and the answer is a 302 to `redirect_uri?code=…&state=…&iss=…`; **on Cancel** it is `error=access_denied`. The scope posted may only narrow what was asked for — an unknown scope, or one the request never named, is refused rather than trimmed. Abuse limits go through `abuse_guard.php` (fail-open): per-IP (`oauthIpHash()`, never the raw address) and, once signed in, per-account (the account id, never an address and never a client_id) requests per hour and per day, over either being 429 with `Retry-After`. **Logging**: one INFO line per decision with `user_id`, `client_id` and the granted scopes, plus a WARNING with `getVisitorIp()` for a rate-limit hit and a refused CSRF token; the code, the state and the redirect query are never logged, and neither is the app's name. `tests/oauth_authorize_test.php` is the regression suite.
- **Connected apps: grants and tokens** (epic #331 step 4/6 — `mcp_tokens.php`, `oauth_server.php`, `pro_profile.php`, `pro_profile_page.php`, `cron/cleanup.php`) — an OAuth access token is an ordinary `mcp_access_tokens` row (see the token-endpoint entry above), so a connection is shown and ended where manual tokens already were; nothing new is stored for it. `mcpTokenList()` tells the two kinds apart — `is_oauth` (the row's `oauth_client_id` is set), `oauth_client_name` (the name registered in `oauth_clients`, falling back to the row's own name when the client is gone) and `grant_created_at` — and returns the same row shape whether or not `migrate_oauth.php` has run, via `mcpTokenGrantColumnsAvailable()`, a column check rather than a `require`, because `oauth_server.php` requires `mcp_tokens.php` and never the other way round; `mcp_token_list` in `pro_profile.php` passes the three fields through, and `mcp_tokens_test.php`'s existing contracts are unchanged. The card has two groups: **Connected apps** — one row per grant, the app's own name, `Read only` / `Read and change`, the connected date and last use — and **Access tokens**, the manual ones as before with the create form; both are drawn from the one `mcp_token_list` answer by the same renderer, and every value goes in with `.text()` because an app names itself on the registration endpoint and that string is attacker-controlled. **Revoke** is the same `mcp_token_revoke` action for both, and stays Pro-independent (the action and `mcpTokenRevoke()`), so a degraded account can still take a credential away: the row holds the access token *and* the refresh token, so setting `revoked_at` ends both — `mcpTokenResolve()` answers nothing for the access token (401 at `mcp.php`) and `oauthRefreshTokenExchange()` answers `invalid_grant` for the refresh, and `oauthGrantExists()` stops counting the pair. Every revoke-all path covers grants with no change, because `mcpTokenRevokeAll()` is scoped by `pro_user_id` alone: a password or email change and both undo links, account deletion, an admin suspension in `abuse_admin.php` and an inactive-account removal in `cron/cleanup.php` each call `mcpTokensRevokeAllFor()`, verified per path in `tests/oauth_grants_test.php`. **Cleanup**, fail-open like `cleanupExpiredMcpTokens()`: `mcpTokenCleanup()`'s expiry branch now also requires `refresh_expires_at` to be past the grace period, because a grant's access token (one hour) always ages out long before its refresh token (90 days) and deleting the row would disconnect a live app — a *revoked* row needs no such guard, since the refresh path refuses it outright and there is nothing left to refresh; `oauthCodeCleanup()` removes authorization codes older than `OAUTH_CODE_SWEEP_SECONDS` (a day) and `oauthClientCleanup()` removes clients with no token row and no activity for `OAUTH_CLIENT_IDLE_SECONDS` (30 days, `COALESCE(last_used_at, created_at)`) — never a client a token still points at, which would strand exactly the orphan `check_oauth.php` reports. `cron/cleanup.php` calls both from `cleanupExpiredOauth()` **after** the token sweep, so a client whose revoked grant was just removed becomes sweepable in the same run. `check_oauth.php` adds the counts: active grants, accounts over the 10-grant cap (a failure), grants whose account is gone (a failure), clients without grants and expired codes the sweep has not reached. `tests/oauth_grants_test.php` is the regression suite.
- **OAuth discovery** (epic #331 step 5/6 — `oauth_metadata.php`, `oauth_server.php`, `mcp.php`, `config.php`) — the step that makes a client find and use the flow above, so it is the one that switches OAuth on. A client learns where to start from the 401 challenge: every 401 now carries `WWW-Authenticate: Bearer realm="Mail Shield", resource_metadata="<base_url>/.well-known/oauth-protected-resource"`, and the missing-token JSON-RPC error names both ways to get a credential (the client's own sign-in flow, or an access token under Profile → Security → Connected apps). `oauth_metadata.php` serves the two documents `.htaccess` rewrites to it — **Protected Resource Metadata** (RFC 9728) at `/.well-known/oauth-protected-resource` and its path-specific form `/.well-known/oauth-protected-resource/mcp` (`resource` = `oauthCanonicalResource()`, so it is the same identifier the authorization endpoint validates a request's `resource` against; `authorization_servers`, `scopes_supported`, `bearer_methods_supported`, `resource_name`), and **Authorization Server Metadata** (RFC 8414) at `/.well-known/oauth-authorization-server` plus the OpenID-Connect-style alias `/.well-known/openid-configuration`, which answers the identical document (`issuer`, the four endpoints, `response_types_supported`, `grant_types_supported`, `code_challenge_methods_supported: ["S256"]`, `token_endpoint_auth_methods_supported: ["none"]`, `scopes_supported`, `authorization_response_iss_parameter_supported: true`). Both are built only from `$config['email']['base_url']` — `oauthIssuer()` returns its *origin* (path dropped, since RFC 8414 wants an origin) and every endpoint is that origin plus a path — never a literal, so they follow `BASE_URL`; both are public, so they carry `Content-Type: application/json`, `Cache-Control: public, max-age=3600` and `Access-Control-Allow-Origin: *` (a browser-based client reads them cross-origin) and answer GET/HEAD only. **Gating**: the documents 404 and the challenge stays the bare `Bearer realm="Mail Shield"` unless `oauthDiscoveryEnabled()` holds — the operator's `OAUTH_ENABLED` switch (env, default off) **and** `oauthAvailable()` (the migration) — so with either missing `mcp.php` is byte for byte what it was before this step and a half-migrated deploy advertises nothing; the OAuth endpoints themselves are unchanged (still `oauthAvailable()` only), and the 403/429/415/405 answers carry no challenge at all. `.htaccess` adds the three `.well-known` rewrites *before* its dotfile block, which already exempts `.well-known/`; `robots.txt` keeps `/oauth/` and `/mcp` disallowed and never blocks `/.well-known/`, and `sitemap.php` is untouched. `tests/oauth_discovery_test.php` is the regression suite (a scripted client walks discovery → register → authorize → token → `tools/list` → `tools/call` through a probe router that emulates those rewrites); `tests/mcp_endpoint_test.php` pins the unchanged challenge while discovery is off.
- **After login** (`after_login.php`, epic #331 step 3/6) — how a page asks to be returned to once the visitor has signed in, without ever becoming an open redirect. The destination is a **route name checked against an allow-list** (`afterLoginRoutes()`, today only `oauth_authorize` → `/oauth/authorize`) plus a query of already-validated parameters, **stored in the session** — the user never sees or carries it, so there is no URL parameter to edit, and `afterLoginUrl()` throws away a route that is no longer in the allow-list, an entry older than `AFTER_LOGIN_TTL_SECONDS` (900), and any value that is not a string or contains a control character. The path always comes from the allow-list and the query is rebuilt with `http_build_query()`, so a value can never smuggle a CR/LF into a `Location` header. `afterLoginTake()` is the single-use read every sign-in path calls instead of the hardcoded `'pro.php'`: the trusted-device, password, 2FA and magic-link branches in `pro_auth.php` (four) and the already-signed-in and magic-link branches in `pro_login.php` (two) — which is also what makes the "Stay signed in" restore resume the request, since the restore happens before that first branch. Adding a route here is the one place an open redirect could be introduced.
- **Address cool-off** (`address_cooldown.php`, table `address_cooldowns` from `migrate_address_cooldowns.php`) — a removed personal address is reserved for the account that held it for `$config['address_cooldown']['months']` (default 6), so nobody else can take it over and receive mail meant for the previous owner. Every path that removes a personal address reserves it first, in the same transaction/step: `mailboxDeleteSticky()` in `mailbox_service.php` (called by `delete_personal` in `index.php`, see #319), `delete_account` in `pro_auth.php`, and the grace-period and inactive-account removals in `cron/cleanup.php` (a deleted account's addresses stay reserved under its old id, so they are blocked for everyone). `create_personal` refuses someone else's reservation with the same "Address already taken" as a live address, lets the owner take it back (which ends the reservation), and `generate` never hands out a reserved local part. Each account holds at most `max_per_user` (default 30) active reservations; adding one more drops the oldest, which is then free. `list_personal` returns the owner's reservations as `cooldown`, shown as "Recently deleted" on `pro_profile_page.php`. There is no foreign key by design; expired rows count as free everywhere and are swept by `cleanupExpiredAddressCooldowns()` in `cron/cleanup.php`. `tests/address_cooldown_test.php` scans that the deletion paths call `addressCooldownAdd()`.
- **Abuse guard** (`abuse_guard.php`, tables from `migrate_abuse_guard.php`, design in `documentaion/ABUSE_PROTECTION.md`) — measures use and quarantines what is abused. **Quarantine = the address' DirectAdmin forwarder is removed**: with no catch-all on the domain Exim then rejects mail to it at RCPT time and `parse.php` never runs; `cron/abuse-guard.php` (every minute) recreates the forwarder when the time is up, retries failed removals, mails the queued notices and logs the busiest addresses hourly. Two tracks, kept apart: an **address under attack** (counted per address in `parse.php`; warning at 50 % of a limit, then quarantine 30 min → 2 h → 12 h inside 24 h, then closed until the owner deletes it or an admin reopens it; attachment overflows count as strikes), and an **account abusing the service** (`generate` / `create_personal` over their per-IP/per-account limits in `index.php`, answered as an ordinary `success: false, rate_limited: true`; warning, then every address of the account quarantined, then a suspension *proposal*). Being spammed never counts against an account. **Only an admin suspends**, in `abuse_admin.php` (same `ADMIN_USER_IDS` gate as `log_viewer.php`): `pro_users.suspended_at` is set, the account's addresses are closed, magic link / password / 2FA login refuse it (`proUserIsSuspended()` in `config.php`), feeds stop, and `proSessionEndIfSuspended()` — called right after `session_start()` on every page that trusts the session, a new such page must call it too — signs a live session out. `dispatchWebhooks()` queues at most `WEBHOOK_MAX_PER_HOUR` deliveries per hook per clock hour. `deleteDirectAdminForwarder()` ends an address' quarantine and skips the DirectAdmin call when the quarantine already removed the forwarder; the quarantine itself uses `directAdminRemoveForwarder()`, which reports the outcome. `list_personal` returns `paused_until` / `closed` per address, shown under the row on `pro_profile_page.php`. `check_forwarders.php` lists quarantined addresses apart, not as drift. Everything on the mail path is fail-open: without the tables, or on a guard error, mail is handled exactly as before. The counters keep IP addresses for two days (stated in `privacy.php`).
- **Paddle Billing** — `pricing.php` + `assets/js/pricing.js` (Paddle.js PricePreview + overlay checkout, client-side `test_`/`live_` token only), plans in `pricing_tiers.php` with **both** environments' price IDs under each plan (`sandbox`/`production`; `paddleTiersForEnvironment()` in `paddle_sync.php` resolves the one `PADDLE_ENVIRONMENT` names into the flat `priceId` everything downstream reads and **throws** — never falls back to the other environment — for an unknown environment or a plan that lacks it, so the switch to the live catalog, and a rollback, is one env change; #350), `welcome.php` as the checkout success page. `paddle_webhook.php` is the notification endpoint (raw-body HMAC check of `Paddle-Signature` against `PADDLE_WEBHOOK_SECRET`; every failure answers non-2xx so Paddle retries); the logic lives in `paddle_sync.php`, which takes an explicit PDO so `tests/paddle_sync_test.php` runs it on SQLite. It writes only `pro_users.pro_expires_at` (+ `account_type = 'pro'` when granting): subscription → end of the paid period (past_due: 7 days' grace; canceled/paused: the moment it stopped), the one-time `once` price → `NULL`. Degradation stays with `cron/cleanup.php`. Paid time is stacked **on top of** the Pro time the account already had (the 60-day trial, a voucher): the remaining time at takeover is kept as `paddle_entitlements.bonus_seconds` and `pro_expires_at` = Paddle target + bonus; renewals never re-add it, after a cancel it runs from the end of paid time, and it is consumed once paid coverage has ended so re-subscribing cannot re-grant it. It never writes below the expiry it found at takeover and never touches a `NULL` it did not write. Payments link to an account by `custom_data.pro_user_id` (set by pricing.js for a signed-in buyer), else by the Paddle customer's email (matched through `email_hash` on both tables, see "Email at rest"); unmatched payments are stored unlinked and linked when a later `customer.*` event matches. Out-of-order events are resolved by `occurred_at`. The webhook sync needs no server-side key. The only server-side call is the customer portal: the Plan card on `pro_profile_page.php` shows **Manage billing** when the account has a linked Paddle payment, and the `billing_portal` action in `pro_profile.php` (same-origin, not Pro-gated) mints a one-time portal URL via `paddle_api.php` with `PADDLE_API_KEY` — a key with only the customer-portal-session permission, never sent to the browser; the customer id comes from `paddlePortalTarget()` (payments linked to this user id), never from the request. Env: `PADDLE_ENVIRONMENT` (required, `sandbox`|`production`, no default — `paddleClientSettings()` in `config.php` fails loudly), `PADDLE_CLIENT_TOKEN`, `PADDLE_WEBHOOK_SECRET`, `PADDLE_API_KEY` (`pdl_sdbx_apikey_`/`pdl_live_apikey_`, checked against the environment by `paddleServerSettings()`). **Sandbox allowlist (#346):** the sandbox notification destination points at the live `paddle_webhook.php`, so while `PADDLE_ENVIRONMENT=sandbox` only the `pro_users.id` in `PADDLE_SANDBOX_USER_IDS` may be granted Pro — `paddle_webhook.php` passes `environment` and `sandbox_user_ids` to `paddleHandleEvent()`, and `paddleApplyEntitlement()` is where the refusal happens: any other account's event is mirrored into the `paddle_*` tables as usual but `pro_users` is left untouched, the outcome reads `sandbox user not allowed`, a `WARNING` with the `user_id` is logged, and the webhook still answers 200 (a refusal, not a failure — Paddle must not retry). A production event ignores the list entirely.
- **Email at rest** (`pii_crypto.php`) — users' registered addresses (`pro_users.email`, `paddle_customers.email`) get two companion columns, added by `migrate_email_encryption.php`: `email_enc`, AES-256-GCM ciphertext of the address as written (`"v1:" . base64(nonce . tag . ct)`, key sha256(`PII_ENCRYPTION_KEY`)), and `email_hash`, a blind index — HMAC-SHA256 hex of `strtolower(trim(address))` under a sub-key of `PII_INDEX_KEY` (normalisation is deliberately *not* the trial's +tag/dot-stripping one). **Writes (phase A, unchanged):** every path that writes `pro_users.email` — `getOrCreateProUser()`, `redeemVoucherForEmail()` and `register_account` (INSERT, then `proUserStoreEmailPii()`, fail-open), and the confirmed email change and its undo in `pro_auth.php` (same UPDATE statement via `piiEmailWriteFields()`) — and `paddleSyncCustomer()` for `paddle_customers` write the plaintext **and** the pair. **Reads (phase B1, current): the plaintext column is never read.** Every lookup by address is `WHERE email_hash = ?` with `piiEmailLookupHash()` (login by password and magic link, registration, voucher redemption, the "address taken" checks, `paddleResolveUser()` joining `paddle_customers.email_hash` to `pro_users.email_hash`, `scrub_logged_emails.php`), and everything that needs the address — mail senders (verification/notice mails in `pro_auth.php` and `pro_profile.php`, the 2FA mails, digests, inactivity warnings), the profile view, the feed title, the TOTP label, the magic-link session — decrypts `email_enc` with `proUserEmail()` / `piiEmailOpen()`, which return null and log an ERROR (with `user_id`, never an address) rather than hand back garbage; callers then send nothing. Fail closed: without keys a lookup matches nothing (a NULL parameter never equals) and account creation/email change is refused via `piiEmailRequireKeys()`. `$_SESSION['pro_user_email']` is kept as server-side session state. `pending_profile_changes.data` still holds a pending new address in plaintext. Phase B2 stops writing the plaintext and nulls it. `tests/pii_crypto_test.php` scans that only the audited code writes `pro_users.email` and that no SQL string reads it (only `migrate_email_encryption.php` and `check_email_encryption.php` compare against it on purpose); `php check_email_encryption.php` audits the rows.
- **`TwoFactorAuth.php`** (`TwoFactorAuth` class) — TOTP (RFC 6238) core library for optional 2FA on Pro password login: secret generation/AES-256-GCM encryption, code/recovery-code verification, `two_factor_attempts` rate limiting, and "remember this browser" trusted-device cookies. The endpoints/UI that consume it live in the Pro tier files above: `pro_auth.php` (`verify_2fa`/`cancel_2fa`, and the `pending_2fa` session challenge inside `password_login`), `pro_profile.php` (`totp_*` and `trusted_devices_*` actions), `pro_profile_page.php` (the Two-factor authentication section of the profile UI). See `documentaion/2FA_DESIGN.md` for the full design, including a "deviations from the original design" section. `php check_totp.php` runs a DB-free CLI smoke test of its crypto paths.
- **Attachments** — files under `attachments/` are not directly web-served: `attachments/.htaccess` denies all direct HTTP access and they are served only by `files.php`, a signed-URL proxy that sends `nosniff` and an RFC 5987 `filename*`. On disk a file keeps the name `<unixtime>_<8 hex>_<sanitized name>`, while `email_attachments.filename` keeps the sender's own name with any path and control characters removed. `MailParser` stores the attachment bytes unmodified (the binary content stream) and keeps a nameless inline image that has a Content-ID as `inline-image.<ext>`. Deleting an address in `index.php` deletes its mail rows, attachment rows and files through `deleteStoredEmailsForTempEmail()` / `unlinkAttachmentFiles()` in `config.php`.
- **Client Agent subsystem** — a mostly separate feature: `client/agent/` (agent.php, install.php, bootstrap.php) is code end users install on their own mail server; it verifies RSA-signed webhooks and stores AES-256-GCM-encrypted local secrets. `client/backend/` (api.php, bootstrap.php) is the manjo.me-side API managing filter scripts/lists (tables documented in `documentaion/backend/DATA_MODEL.md`: `mailfilter_scripts`, `mailfilter_whitelist`/`blacklist`, `mailfilter_reported_senders`, `mailfilter_webhook_log`). Root-level `client_agent_*.php` files (`api`, `download`, `install_download`, `manage`) are the public entry points into this subsystem. Read `documentaion/agent/ARCHITECTURE.md` and `documentaion/backend/*.md` before changing this area — it has its own security model (RSA signing, key rotation via `cron/rotate_signing_keys.php`) distinct from the rest of the app.
- **`blog.php`** — renders markdown files from `blog/*.md` as a minimal blog. Rebuilt by Redesign 20 on the same shell as `faq.php` (which Redesign 19 rebuilt): an index plus long-form prose. Both are public pages that nevertheless sit in the *app* style group, so they load Bootstrap.
- **`assets/js/sw.js`** — a small service-worker cache for the static shell, registered by `assets/js/app.js`. `PRECACHE_URLS` must be kept in step with the real routes — it names `/`, `/index.php`, `/inbox.php`, the Mail Shield stylesheets, `site.webmanifest` and the two favicons — and `CACHE_NAME` must be **bumped whenever that list changes**, because the `activate` handler only evicts caches whose key differs; an unbumped list leaves a stale entry serving the old shell.
- **`log_viewer.php`** — the admin area, in the app shell (`partials/admin_head.php` / `admin_foot.php`: Bootstrap bridge + `partials/nav.php`, then the tab row in `partials/admin_tabs.php`). Three views by `?view=`: `overview` (default) — a read-only system snapshot from `adminOverview()` in `admin_overview.php` (accounts, addresses, incoming mail, the webhook queue, the abuse guard, log volume, health/config flags reported as set/missing, never values or user addresses, and a "Needs attention" list that also flags crons that look stalled); `logs` — `system_logs` with level/search/date filters, paging and a live tail (`?format=json` returns the rows); `types` — the `hidden_log_types` overrides. `abuse_admin.php`, the abuse guard's admin page, is the fourth tab and uses the same shell. Access is limited to the account ids in `ADMIN_USER_IDS` (comma-separated `pro_users.id`s, checked by `isAdminUser()` in `config.php`); unset means nobody gets in. `partials/nav.php` shows an **Admin** link to those accounts only — the pages enforce the gate themselves. Every figure in `adminOverview()` is fail-soft (a missing table blanks it), and time windows are computed in the database's clock, because PHP's and MySQL's time zones can differ.
- **`debug_logger.php`** — JSON-lines file logger independent of the DB, used by mail-parsing code so a logging failure can't cascade into a parsing failure.

## Conventions worth knowing

- Database access uses PDO with prepared statements (`$pdo->prepare(...)->execute([...])`) — follow this pattern for any new query; do not interpolate user input into SQL.
- User-supplied identifiers (e.g. the temp address in `index.php`) are validated with a strict regex (`^[a-f0-9]{8,16}$`) before being used in queries or lookups — apply the same "validate then look up" pattern for new address/ID handling.
- Never log a user's email address (`pro_users.email`, a pending new address, an address typed into a login/registration form). Log `user_id` when an account exists — a sent magic link or verification mail always has one — and `emailLogContext()` / `emailLogRef()` from `email_log_ref.php` (a 16-hex HMAC under a sub-key of `PRO_TRIAL_HASH_KEY`, nothing at all without the key) only when no account matches. `login_attempts.email` holds that reference too, never the address. Service-domain addresses (temp inboxes) are not user addresses and may be logged. `tests/email_log_ref_test.php` scans for regressions.
- `detectSuspiciousPatterns()` + `logMessage('WARNING', ...)` is used in `index.php` to flag and log potentially malicious input on POST actions before they're processed further.
- This codebase has had repeated rounds of Semgrep-driven security hardening (see git log: "Sec issues fixed in index", "nosemgrep" commits) — when Semgrep flags something, prefer fixing the underlying issue over adding a `// nosemgrep` suppression; only suppress with a comment explaining why it's a false positive.

## Frontend conventions

The enforceable subset. The full spec is `documentaion/REDESIGN_BRIEF.md` — §11 (CSS layering), §12 (hard rules), §14 (SEO guardrails). If you are about to write frontend code and have not read those, read them first.

- New CSS classes are prefixed `ms-`. Colours and sizes come from the `--ms-*` tokens in `assets/css/mailshield.css` — never a raw hex value, and never a hardcoded `px`/`rem` font size.
- **Never hardcode the mail domain in copy** — render `$config['email']['domain']` so example addresses cannot lie if the domain changes. **Never hardcode the origin** — use `$config['email']['base_url']`. (`robots.txt` is the sole documented exception, because it is static.)
- **Never claim a feature the code lacks.** Brief §9 is the inventory; copy may only promise what is in it. The two current traps: there is **no public API** (anything beyond a `Coming` badge is a lie) and **no browser/web push** (never mention it at all).
- Retention and tier facts, which copy keeps getting wrong: free timed addresses last **24 hours**, Pro **1–7 days**; sticky addresses are **Pro-only, max 10**; every new account starts with a **Pro trial of `$config['trial']['days']` days** (default 60, once per email address — render the number, never write it into copy, and fall back to the pre-trial wording at 0), after which Pro requires a **voucher code** on the public site — the nav and sitemap publish **no prices**, and the landing page publishes exactly one: the Pro card's "From €x" (the monthly Pro price in the visitor's currency), which `assets/js/landing-price.js` fetches from `Paddle.PricePreview()` and shows on **production only** (`pricingLandingConfig()` in `pricing_helpers.php`, the same country detection as `pricing.php`) — never write an amount into the markup; on sandbox, without JS or when Paddle is unreachable the card keeps the price-free "Monthly, yearly or once / See prices" wording, and no Paddle script is loaded at all. The full prices are on `pricing.php` (Paddle checkout): since #347 linked from the footer and the landing plans card, but still not from the nav or `sitemap.php`, `noindex` while `PADDLE_ENVIRONMENT=sandbox`, plans edited in `pricing_tiers.php`, prices shown only as Paddle's `formattedTotals`, and checkout closed — each card carries a note in place of Subscribe, and `assets/js/pricing.js` refuses to open `Paddle.Checkout.open()` — except on production or for a signed-in `pro_users.id` in `PADDLE_SANDBOX_USER_IDS` (#346). A completed checkout grants Pro through `paddle_webhook.php` (see the Paddle Billing entry under Architecture) — but only once the notification destination is set up, so copy must not promise instant activation.
- Animation is sparing: no loops, no scroll-triggered motion, no hover `transform`, and every animation sits inside the `prefers-reduced-motion` guard.
- **Google Analytics is consent-gated and public-pages-only (#313, brief §12.10).** The one snippet lives in `partials/analytics.php`, included by `partials/public_head.php` (unless the page sets `$msPage['analytics'] = false`, as `welcome.php` does) and directly by `faq.php`/`blog.php`, which carry their own `<head>`. It never requests `gtag.js` itself — it hands the measurement id to `assets/js/consent.js`, which shows the `.ms-consent` notice and loads `gtag.js` only after Accept, remembering the choice in `localStorage`. Never add the partial to an app, auth or checkout page (`inbox.php`, `pro*.php`, `pro_login.php`, `pro_logout.php`, `register.php`, `welcome.php`).
- `htmlspecialchars()` every PHP value printed into HTML; `escapeHtml()` every value interpolated in `assets/js/app.js` — mail headers are attacker-controlled.
- Check 375 / 768 / 1024 / 1440px. Wide content (tables, code, the inbox list) scrolls **inside its own container, never the page**.
